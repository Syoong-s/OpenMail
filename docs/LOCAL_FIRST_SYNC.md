# 本地即时操作与后台同步

## 交互与同步规则

已读、置顶、移动、归档和移入废纸篓先提交本地 SQLite，再更新界面。操作与后台网络连接使用不同执行通道，连续本地操作按点击顺序提交。退出时完成已接受的本地提交，未同步操作保存在数据库中，重新启动后继续处理。

后台沿用设置中的同步间隔（服务默认 60 秒，最短 15 秒），先发送积累的修改，再拉取服务器状态。手动同步也会发送队列。无需每次点击都连接服务器。复制、永久删除和文件夹管理仍使用需要服务器确认的原有操作路径。

- 同一邮件的同一种标记只保留最后一个意图；按账户、文件夹、UIDVALIDITY、目标值组合，最多 100 封一批发送。
- 确认响应只清理对应版本的意图，不清除网络请求期间发生的新修改。
- 移动保留本地邮件 ID，分别记录原始远程 UID 与当前本地目标。发送前反复移动可合并，发送期间再次移动则作为后续意图处理。
- 移动收到 COPYUID 后更新对应关系。断线或缺失映射时，核对来源 UIDVALIDITY、目标 Message-ID 与完整 MIME 内容；结果不确定时保留队列并退避重试，不盲目重发 MOVE 或删除另一份副本。没有可用 Message-ID、UID 世代变化或两份完全相同副本等情况可能需要用户核对服务器。
- 失败保留本地显示和队列，并在同步状态中提示。暂停账户不会发送修改。队列恢复不会阻止同一目标文件夹接收其他新邮件。

“完成”使用账户的实际归档文件夹，取消完成移回收件箱。“已完成”列表包含已归档邮件；旧的本地完成标记在后续同步中分批转换为归档操作。未发现归档文件夹时需要在文件夹管理中设置映射，不会仅隐藏邮件冒充归档。RFC `\All` 与 `\Archive` 含义不同，因此“所有邮件”不会自动被视为归档；需要此目标的账户可显式设置归档映射。

## 界面更新

- 已读状态、联系人未读气泡、正文卡片的图标状态由本地提交驱动。移出当前对话范围的邮件从保留的时间线中移除。
- 状态变化优先原位修改；成员或顺序变化复用未变化的邮件行、联系人行和正文浏览器。最多保留 200 个离屏行，退出时释放引用及回调。
- 最近访问的列表查询按数据修订号、影响查询的偏好与筛选范围缓存，最多 8 份、20,000 个邮件条目引用、30 秒；窗口尺寸、通知记录等写入不会使缓存失效。联系人查询仍读取实时范围与索引状态。
- 聚焦卡片拥有独立的原生列表，不再等待完整邮箱查询、历史计数和普通邮件行构建。切回同一范围时立即恢复现有控件和最近数量，后台更新；首次访问显示数量待定的卡片。最多保留 8 份按账户、视图和分类策略隔离的简短快照，数量可能短暂显示上次结果，当前查询完成后原位刷新。
- Windows 预热并复用最多两个空闲 WebView2 控件；正文在实际排版尺寸稳定后显示。测量期间使用空裁剪区域，保持浏览器正常布局，避免隐藏控件得到 1 像素视口。测量异常有两秒显示后备机制。
- 侧栏只在外层行绘制高亮，订阅状态不再降低文字亮度，固定图标不随鼠标离开消失。新邮件通知基于账户与邮件标识，移动、复制和 UID 变化不会冒充新来信。
- 邮件气泡原有的单项更多菜单改为直接的废纸篓按钮。对话发送区将收件人与主题分两行，点击可编辑；发件账号显示别名或简短地址标识，提示与菜单保留完整邮箱。发送箭头由 Cairo 矢量绘制，随主题切换前景色，并保持圆形按钮内居中。

## 调研依据

采用 [Android 官方离线优先架构中的本地权威数据源、持久化写入队列和重试原则](https://developer.android.com/topic/architecture/data-layer/offline-first)，应用到现有 SQLite/IMAP 架构。移动及恢复遵循 [RFC 6851 IMAP MOVE](https://www.rfc-editor.org/rfc/rfc6851.html)；特殊文件夹区分依据 [RFC 6154](https://www.rfc-editor.org/rfc/rfc6154.html)。这些是设计依据，不表示使用 Android 运行库或更换邮箱协议。

## 运行与验证

本次无需新增依赖或编译原生 DLL。目标是现有 Windows/Linux 桌面应用；本次变更不涉及 HPC 部署。正常运行方式不变：Linux 使用 `./run.sh --demo`；Windows 使用按 [BUILDING.md](BUILDING.md) 构建的 TeleMail 包。

测试解释器为 WSL Python 3.14.4 与现有 Windows 包内 CPython 3.14.5。原生验收使用已有 GTK 3.24 与 WebView2；Linux 富文本运行要求 WebKitGTK 4.1，本次 WSL 环境缺少该库，未完成 Linux 富文本界面验收。所有验收使用临时演示资料目录和合成邮件，禁止访问真实 IMAP/SMTP。

从仓库根目录执行：

```sh
python3 -B tools/run_tests.py --output .runtime/local-first-tests
python3 -B tools/verify_mail_responsiveness.py --output .runtime/local-first-desktop
python3 -B tools/verify_focus_composer.py --output .runtime/focus-composer-native
```

第二条需要完整图形运行库。在 Windows 下使用已有包内 Python 执行同一个脚本；脚本从解释器位置解析运行库。完整后端测试可通过 `--bundle` 指定已有包，TLS 测试通过 `--qa-openssl-dir` 指定已有 OpenSSL CLI，隔离生成测试配置。

第三条同样使用完整图形运行库。它故意阻塞查询工作线程一秒，验证四张卡片在查询完成前映射到屏幕、控件身份不变、数量后续更新，以及分组往返、收件人编辑、发件账号切换、发送图标居中和直接删除气泡。深浅主题截图使用合成资料；截图临时显示可用的发送按钮外观，但演示模式仍禁止发送。

`test_mail_mutations.py` 覆盖离线保存、重启恢复、批量原子性、后续修改、UIDVALIDITY 防护、丢失响应、缺少 COPYUID、歧义副本、通知去重、旧完成迁移及文件夹重命名。原生验收脚本检查控件身份、实际 GTK 样式、正文显示就绪、聚焦卡片、未读徽标和删除气泡，写出 JSON 指标与 GTK 侧栏截图。

两端完整后端测试各运行 370 项、零失败及错误；Linux 跳过 6 项平台测试，Windows 跳过 5 项。Windows 的 TLS 测试使用已有 OpenSSL CLI 与临时配置完成，未排除测试套件。

Windows 原生验收的 7 项检查通过。合成邮箱（160 封新增 HTML 邮件，每页 100 行）测得：四次正文打开至排版就绪约 0.30–0.45 秒；本地已读更新约 0.20 秒；返回聚焦卡片约 0.080 秒；整页行完成约 0.71 秒，累计复用 199 个原生行。数值包含实际 GTK/WebView2 调度，会随机器负载变化。尚未与 Spark 在相同真实邮箱数据上做对照，不能据此声称全面达到其性能。

详细测试结果保存在本地 `.runtime/local-first-tests/`、`.runtime/local-first-windows-tests/` 与 `.runtime/local-first-windows/`。这些报告和截图不属于发行产物；源码变更不会自动更新已安装的旧程序。
